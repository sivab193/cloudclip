# Hosted Sites: public static-site hosting at /s/&lt;slug&gt;

CloudClip gains a "Hosted Sites" feature: owners (via Firebase auth) or agents (via a `cc_pub_` publisher key) upload an HTML file or a ZIP static build, which is extracted, stored as base64 inside a single MongoDB deployment document, and served publicly at `/s/<slug>`. Redeploys keep the slug and atomically swap the active deployment pointer once the new files are fully stored. Sites can be public or password-protected, with the gate backed by scrypt hashing and an HMAC host-only access cookie. The archive extractor enforces path-safety, size, file-count, and compression-ratio limits; the serving route adds `nosniff`, a SPA fallback, and strict MIME typing.

Watch for: the central isolation claim is unsound (**confirmed, critical**) — `/s/*` is served on the CloudClip app's own origin via a Vercel *rewrite* (reverse proxy), so user-published JavaScript runs same-origin with the app and can read the Firebase auth token in `localStorage`, the master key in `sessionStorage`, and call `/api/*` with the victim's ambient credentials. Everything else (path safety, password gate, ownership scoping, publish transaction) is solid; this one gap defeats the entire security model the rest of the code carefully builds.

**Verdict**: NEEDS_CHANGES

## High-level view

The feature serves untrusted user HTML/JS from `/s/<slug>`. The backend route (`siteServe.ts`) is written as if it were on a cookieless, separate origin — it sets no CloudClip cookies, sends `nosniff`, and the code comments repeatedly assert "user HTML must never run on the CloudClip app origin." But the only thing routing traffic to that backend is the Vercel rewrite `"/s/:path*" -> "https://api-us.cclip.cc/s/:path*"`. A rewrite is a server-side proxy, not a redirect: the browser's address bar and origin stay `https://cclip.cc`. So the served site is same-origin with the app, and the app stores its Firebase ID/refresh token in `localStorage` (default web persistence) and the vault master key in `sessionStorage` — both readable by any script on `cclip.cc`. The isolation posture is the opposite of what the comments claim.

Archive extraction is careful and the path-safety model is sound. `isSafePath` rejects absolute paths, `..`, backslashes, and NUL; extraction additionally blocks dotfiles, `.git`, and `__macosx`, enforces 10 MB archive / 12 MB extracted / 2000-file limits, and guards a >200× compression ratio. Served paths are re-validated with the same `isSafePath` and resolved by exact match against the deployment's stored file list, so there is no filesystem to traverse and no way to read another deployment's files — the `deploymentId` is pinned from the site's own `activeDeploymentId`.

The password gate is cryptographically reasonable but inherits the origin problem. scrypt with a per-site salt and `timingSafeEqual` is fine (argon2 would be better but scrypt is defensible). The access token is `HMAC(secret, "slug:deploymentId")`, so redeploying rotates `deploymentId` and silently invalidates old cookies — a good property. The cookie is `HttpOnly; Secure; SameSite=Lax; Path=/s/<slug>/`. Two caveats: the HMAC secret falls back to `FIREBASE_PRIVATE_KEY` if neither sites-specific var is set (key reuse across unrelated subsystems), and because the gate ultimately protects content served on the app origin, any already-compromised site on the same origin moots it.

Ownership scoping is correct throughout: every owner route filters by `ownerId: req.user.uid`, cross-owner reads/deletes return 404, revoked publisher keys are rejected at auth time, and the raw key is shown once and stored only as a SHA-256 hash. The publish transaction never exposes a partial site — files are stored before the active pointer flips, a failed first deploy rolls back the reserved slug, and a failed redeploy leaves the prior version serving. These are all verified by the test suite.

The scrypt and HMAC comparisons are constant-time, but the publisher-key lookup compares `keyHash` with a plain `===` string compare after an indexed prefix lookup; given the hash is SHA-256 of a 24-byte random secret this is low-risk, but it's an inconsistency with the constant-time comparisons used everywhere else.

<summary>Issues (6)</summary>

1. **Same-origin serving defeats all isolation (critical)** — `/s/*` is a Vercel rewrite to the backend, so user JS runs on `cclip.cc` and can read the Firebase token (`localStorage`), master key (`sessionStorage`), and call `/api/*` with the victim's credentials. Serve hosted sites from a distinct origin (e.g. `*.cclip.site` or `sites.cclip.cc` with per-slug subdomains), not a path on the app origin. A path-based rewrite cannot provide origin isolation.
2. **No CSP/sandbox on served content (high)** — `siteServe.ts` deliberately omits CSP and `sandbox` ("would break legitimate sites"). On the current same-origin setup that leaves nothing between user JS and the app. Until a separate origin exists, add a restrictive CSP or `Content-Security-Policy: sandbox` to served HTML; once on a separate origin it's defense-in-depth.
3. **HMAC/session secret falls back to `FIREBASE_PRIVATE_KEY` (medium)** — `sessionSecret()` in `siteServe.ts:19-20` chains to `SHARE_TOKEN_ENCRYPTION_KEY` then `FIREBASE_PRIVATE_KEY`. Reusing the Firebase signing key for site access cookies couples unrelated trust domains. Require `SITES_SESSION_SECRET` explicitly and fail closed if unset rather than borrowing another subsystem's key.
4. **Publisher-key hash compared with `===` (low)** — `publisherAuth.ts:37` uses `k.keyHash === expectedHash` instead of `timingSafeEqual`, inconsistent with the constant-time comparisons elsewhere. Low practical risk (SHA-256 of random secret) but should match the rest of the codebase.
5. **SVG served inline on a (currently) same-origin path (medium)** — `image/svg+xml` is in the MIME map; an SVG navigated to directly executes script. Harmless on a sandboxed separate origin, but on the current same-origin path it's another script-execution vector. Resolved by fixing issue 1, or serve SVG with `Content-Disposition: attachment` / a sandboxing CSP.
6. **Per-document storage ceiling is a soft DoS / correctness cliff (low)** — 12 MB extracted base64 (~16 MB encoded) sits right at Mongo's 16 MB BSON document cap; a build near the limit could fail the `updateOne` store step after passing extraction. The transaction handles it (deployment marked `failed`, prior version keeps serving), so it's a correctness/UX cliff rather than a vulnerability. Consider lowering the extracted cap to leave BSON headroom, or move to object storage via the existing `siteStorage` seam.

### Same-origin serving via Vercel rewrite — the isolation claim is false

`siteServe.ts` and `app.ts` are written around one premise, stated in a comment in `app.ts`: *"User HTML must never run on the CloudClip app origin with app cookies."* The route honors its half of that: it sets no CloudClip cookies, emits `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `X-Frame-Options: SAMEORIGIN`, and the app-level helmet middleware is explicitly skipped for `/s/` so the app CSP doesn't apply.

The premise is broken by the routing layer. `app/vercel.json`:

```json
{ "source": "/s/:path*", "destination": "https://api-us.cclip.cc/s/:path*" }
```

This is a **rewrite**, which Vercel serves as a reverse proxy. The user's browser requests `https://cclip.cc/s/<slug>/…`, Vercel fetches from the backend server-side, and returns the bytes — the document's origin remains `https://cclip.cc`, identical to the CloudClip app. There is no origin boundary.

What that exposes, confirmed by reading the web client:

- `app/firebaseConfig.ts:22-23` uses `getAuth(app)` on web, whose default persistence is `browserLocalPersistence` — the Firebase **ID and refresh tokens live in `localStorage` on `cclip.cc`**. `apiService.ts` sends them as `Authorization: Bearer <token>` to `/api/*`.
- `app/service/keyStore.web.ts` stores the vault **master key in `sessionStorage`** on the same origin.
- `app/service/syncEngine.ts` / `deviceService.ts` keep sync state and the web device ID in `AsyncStorage`, which on web is `localStorage`.

User-published JavaScript at `/s/<slug>` runs on `cclip.cc` and can read all of the above and issue same-origin `fetch('/api/…')` calls carrying the victim's token. `nosniff` and `no-referrer` do nothing against this; they address different threats. The `vercel.json` comment — *"proxied to the backend and must set their own headers so user HTML can render"* — describes the mechanism that creates the vulnerability.

The fix is architectural, not a header: hosted sites must be served from an origin distinct from the app — a separate domain, or per-slug subdomains like `<slug>.cclip.site`. The backend route is already origin-agnostic and would work unchanged behind a different host; the `siteUrl`/`SITES_PUBLIC_ORIGIN` plumbing already contemplates a configurable public origin, so the serving code is ready for this — only the public origin and the rewrite need to change. Per the steering note, reusing the `/s` path (and breaking old `/s/` share links, now moved to `/t/`) is an accepted product decision; that path *rename* is fine. What is not fine is that the path resolves to the **same origin** as the app. Keeping the `/s` path is compatible with the fix as long as `/s` lives on a different host than the authenticated app.

Until a separate origin is in place, every other control here is protecting content that an attacker's co-hosted script can already reach, so the realistic interim mitigation is a strict per-response CSP / `sandbox` on served HTML (see below), accepting that it will constrain legitimate sites.

### Path traversal and zip-slip — sound, no escape found

The extractor (`sites.ts: extractUpload`) and the served-path resolver (`siteServe.ts`) were the highest-risk area for file escape, and I could not find a traversal.

`isSafePath` rejects empty input, leading `/`, any `\`, any NUL, and any segment that is empty, `.`, or `..`. Extraction applies it to every ZIP entry and additionally rejects `.git` top-level, `.env*`, and `__macosx`. fflate's `unzipSync` yields already-joined entry names, and directory entries (`foo/`) are filtered out before validation. The single-folder-prefix logic strips a `dist/`-style wrapper by exact prefix match and re-checks for a root `index.html` afterward, and a post-strip lowercase `seen` set rejects case-collision duplicates.

On the serve side the requested path is decoded once, directory requests get `index.html` appended, then `isSafePath` runs again before lookup. Critically, there is no filesystem: `readDeploymentFile` does `deployment.files.find(f => f.path === path)` — an exact string match against the stored, already-normalized paths of **one** deployment. The `deploymentId` comes from the looked-up site's own `activeDeploymentId`, never from user input, so there is no way to address another site's or another deployment's files even if a crafted path slipped through. The SPA fallback only triggers for paths without a non-fallback extension and only ever reads `index.html` of the same deployment.

One note rather than a vulnerability: `isSafePath` treats a bare `index.html` request path as fine, and percent-encoded traversal (`%2e%2e`) is neutralized because `decodeURIComponent` runs *before* `isSafePath`, so `..` is caught after decoding. Double-encoding doesn't help an attacker since only one decode pass happens and the result is still validated.

### Password gate — cryptographically fine, redeploy-invalidation is a nice property

scrypt with a 16-byte per-site salt, 32-byte output, compared via `timingSafeEqual` with a length guard (`sites.ts: verifyPassword`). The plan's own comment concedes argon2id would be preferable; scrypt is an acceptable Node-built-in substitute. The locked page escapes the `next` value's quotes and the unlock handler clamps `next` to a `/s/<slug>/` prefix, so the redirect can't be pointed off-path.

The access token is `HMAC-SHA256(secret, "slug:deploymentId")`, base64url, delivered as `ccsite_access_<slug>=…; HttpOnly; Secure; SameSite=Lax; Path=/s/<slug>/`. Binding the token to `deploymentId` means a redeploy (new `deploymentId`) invalidates every previously issued cookie automatically — the test suite's redeploy case and the per-slug cookie path both confirm the scoping. I could not find a forgery or bypass of the gate itself: the cookie is compared constant-time against the recomputed HMAC, and an empty `sessionSecret()` fails closed (`hasValidAccess` returns false, unlock returns 503).

The real caveat is inherited, not local: the gate protects content that is served on the app origin, so on the current setup a password site is only as isolated as the weakest co-hosted public site. And `sessionSecret()` borrowing `FIREBASE_PRIVATE_KEY` as a last-resort signing key couples the site-cookie trust domain to Firebase's — it should require its own secret and fail closed.

### Ownership and publisher keys

Deployment listing is gated through a parent-site ownership check before querying `SiteDeployment`, so it can't be used to enumerate another owner's deployments directly. A cross-owner probe of a site/deployment/key ID returns 404, not 403, so IDs aren't confirmed to attackers. Revocation sets `revokedAt` and the auth query filters `revokedAt: null`, so a revoked key stops working on the next request (confirmed by the revoke test). The one local nit is the non-constant-time `===` on the key-hash compare noted above.

### Publish transaction — the rollback and swap ordering

The non-obvious, correct choices worth calling out: extraction/validation runs *before* any DB write; a failure after site creation deletes the half-created site and its deployments so the reserved slug is freed (not left dangling); `deploy` flips `site.activeDeploymentId` only *after* files are fully stored, so a store failure leaves the active pointer untouched — a first deploy fails with no live site, a redeploy fails with the prior version still serving (both asserted by tests). Delete flips `status=deleted` and nulls `activeDeploymentId` *first* so serving stops immediately (`lookupActiveSite` filters `status:'active'`), then best-effort drops deployment docs — the correctness-critical step is synchronous, the cleanup is fire-and-forget.

### Extraction DoS bounds — mostly covered, one cliff

Archive upload is capped at 10 MB (multer `fileSize` and a re-check in `extractUpload`), extracted total at 12 MB, file count at 2000, and a >200× compression ratio is rejected as a zip-bomb guard — computed from the real post-decompression `byteLength` sum, so it can't be fooled by lying ZIP metadata. These bound the obvious memory/CPU vectors for a single upload. fflate's `unzipSync` is synchronous and decompresses the whole archive in memory before the ratio check runs, so a crafted ~10 MB archive can still momentarily allocate up to ~2 GB before the 12 MB extracted check trips — worth noting for a synchronous in-process extractor, though the archive cap keeps it bounded. The storage cliff at Mongo's 16 MB BSON limit is the main residual concern (issue 6).
